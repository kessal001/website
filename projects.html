parquet_info

A terminal-first inspector for understanding Parquet files quickly—before opening a notebook, launching a data platform or writing exploratory code.

View repository ↗
Role
Creator & maintainer
Stack
Python · PyArrow · Rich
Format
Command-line interface
Status
Beta · MIT licence

The problem

Exploration often starts with too much ceremony.

A Parquet file may arrive without context. Before using it, an analyst needs to know its dimensions, columns, types, representative values and possible quality issues. The usual route can require a notebook, a dataframe library or a heavier BI environment for what should be an immediate inspection.

The approach

Start cheap, then narrow the question.

The tool begins with lightweight schema and metadata inspection. From there, the user can preview rows, profile selected columns, search text values or move into an interactive browser. The workflow is progressive: inspect first, then spend computation only where it adds information.

A

Capabilities

One tool, four levels of inquiry

  1. 01

    Inspect

    Read schema, metadata and sample rows without loading a full analytical environment.

  2. 02

    Profile

    Review nulls, distinct counts, ranges, averages and frequent values for relevant columns.

  3. 03

    Search & browse

    Find text across the dataset or inspect its contents interactively from the terminal.

  4. 04

    Automate

    Export structured JSON output so the same inspection can become part of a repeatable workflow.

Example workflow

From overview to evidence.

A single command can combine profiling with a targeted search, while keeping the output suitable for a plain terminal.

parquet-info examples\demo_inventory.parquet \
  --profile \
  --search priority \
  --format plain

Designed as a small, focused utility: explicit commands, readable output, tests and continuous integration around the core inspection workflow.

Epidemic Lab

An interactive SIR epidemic simulator that turns a system of differential equations into a visual, explorable learning experience in the browser.

Numerics

Local in the browser

The problem

Mathematical models are precise, but rarely tangible.

The SIR model is compact on paper, yet its dynamics are easier to understand when parameters can be changed and their consequences observed. A useful teaching tool must preserve the mathematics while making transmission, removal, thresholds and the epidemic peak visible.

The approach

Make every assumption observable.

The application exposes population, initial conditions, transmission and removal rates as interactive controls. It integrates the equations numerically, redraws the SIR curves and calculates R₀ and the infection peak, pairing experimentation with a page that explains the model and its limits.

B

From equations to interaction

A model designed to be explored

  1. 01

    Simulate

    Integrate the SIR system with a fourth-order Runge–Kutta method and plot its three compartments.

  2. 02

    Experiment

    Change the population, initial infections, β, γ and duration, or begin from a preset scenario.

  3. 03

    Interpret

    Relate the reproduction number and infection peak to the parameters and the changing susceptible population.

  4. 04

    Learn safely

    Run entirely in the browser with no account, database or API, while clearly stating the scientific limits of SIR.

Originally developed as a 2020 school project and rebuilt in 2026: modernized from an obsolete prototype into an autonomous, responsive application for contemporary browsers.

MyShelfie

A distributed, multiplayer implementation of the My Shelfie board game, developed by a four-person team for the Software Engineering final project at Politecnico di Milano.

View repository ↗
Role
Software engineer · team of four
Stack
Java 19 · JavaFX · Maven
Architecture
Client–server · RMI & sockets
Result
30L/30

The challenge

A board game becomes a distributed system.

Recreating the complete rules was only one part of the assignment. The application also had to coordinate concurrent matches, remote players, state changes and disconnections while supporting different network protocols and two distinct user interfaces.

The approach

Separate domain, communication and presentation.

The team structured the application around a client–server architecture with shared game logic, event-driven flows and interchangeable communication and interface layers. The same system can operate through sockets or RMI and through either a graphical JavaFX client or a terminal UI.

C

Engineering scope

Beyond the basic game requirements

  1. 01

    Multiple games

    Host concurrent matches and keep each game’s players, state and lifecycle isolated on the server.

  2. 02

    Resilient clients

    Handle client disconnections and reconnections while preserving the active match and player state.

  3. 03

    Two protocols, two UIs

    Support both Socket and RMI networking alongside a responsive JavaFX GUI and a terminal interface.

  4. 04

    Test & document

    Use Maven, JUnit, JaCoCo coverage reports, UML and JavaDoc to support a large collaborative codebase.

The project was presented in June 2023, ahead of the official deadline, and received the highest grade with honours. The repository remains a record of both the application and the team’s engineering process.
